# LunchTogether — Зміст презентації (захист дипломної роботи)

> 6 слайдів. Хронометраж: ~4–5 хв на слайди + ~5–6 хв жива демонстрація.
> Слайди свідомо лаконічні — основна вага на демо.

---

## Слайд 1 — Титульний

- **Назва:** LunchTogether
- **Підзаголовок:** Координація спільних обідів у команді: від замовлення до розрахунку
- Ваше ім'я · Тема дипломної роботи · Керівник · Рік
- Фон: мокап головного дашборду

---

## Слайд 2 — Бізнес-проблема

Заголовок: **Проблема спільних обідів у команді**

- 💬 **Координація:** десятки повідомлень у чаті — «хто що бере?»
- 💸 **Гроші:** платить хтось один → ручний облік «хто кому винен»
- 🔁 **Повторюваність:** ті самі заклади й меню переписуються щотижня
- 📉 **Непрозорість:** немає історії, статистики, звірених розрахунків

> **Головна теза:** проблема не в тому, щоб *замовити* їжу — а в координації
> та обліку грошей у стабільній групі, що замовляє регулярно.

## Слайд 3 — Конкуренти та незакрита ніша

Заголовок: **Що пропонує ринок — і чого там бракує**

| Можливість | Glovo / Bolt Food (Group Order) | Splitwise | Чат + Google Sheets | **LunchTogether** |
|---|:---:|:---:|:---:|:---:|
| Спільне замовлення | ✅ (1 доставка) | ❌ | ⚠️ вручну | ✅ |
| Не прив'язано до сервісу доставки | ❌ | — | ✅ | ✅ |
| Постійний баланс-реєстр між замовленнями | ❌ | ✅ | ⚠️ вручну | ✅ |
| Пам'ять закладів і страв групи | ❌ | ❌ | ⚠️ | ✅ |
| Ролі та права в групі | ❌ | ❌ | ❌ | ✅ |
| Статистика й аналітика | ❌ | ⚠️ | ❌ | ✅ |

> **Теза:** маркетплейси доставки закривають *разовий* кошик і кидають облік;
> Splitwise рахує борги, але не знає про меню й замовлення; таблиці — ручна праця.
> Ніша на перетині лишається вільною.

## Слайд 4 — Що вирішує LunchTogether

Заголовок: **Унікальна цінність — шар координації + обліку**

**1. Два контексти роботи**
Глобальний (користувач) та контекст окремої групи з ізоляцією даних.

**2. Замовлення як керований процес**
Життєвий цикл: `Ініційовано → Підтверджено → Замовлено → Завершено`
з правами на кожному кроці.

**3. Автоматичний фінансовий реєстр**
При завершенні замовлення баланси учасників перераховуються автоматично,
з повною історією змін.

> **Теза:** ми не конкуруємо з доставкою — ми **доповнюємо** її
> організаційно-обліковим шаром, якого там немає.

## Слайд 5 — Архітектура (оглядово)

Заголовок: **Технічна архітектура**

Проста діаграма трьох шарів:

```
┌─────────────────────────────────────────────┐
│  Frontend — React 19 + TypeScript            │
│  Vite · Redux Toolkit + RTK Query            │
│  Tailwind CSS + Radix UI                     │
└───────────────────┬─────────────────────────┘
                    │  REST / JSON (JWT cookie)
┌───────────────────┴─────────────────────────┐
│  Backend — FastAPI (Python 3.12, async)      │
│  Шари: API → Workflows → Repositories → Models│
└───────────────────┬─────────────────────────┘
                    │  async SQLAlchemy 2.0
┌───────────────────┴─────────────────────────┐
│  PostgreSQL · міграції Alembic                │
└───────────────────────────────────────────────┘
```

- **Auth:** JWT у HTTP-only cookie + гранулярні права на рівні групи
- **Наскрізна типізація:** TypeScript (фронт) · Pydantic (бекенд)

> **Теза:** кожна бізнес-дія — окремий workflow-клас, домени ізольовані,
> чітке розділення відповідальності.

---

## Слайд 6 — Інфраструктура та якість + підсумок

Заголовок: **Готовність до експлуатації**

- **CI/CD:** GitHub Actions — тести (pytest + Ruff) і build на кожен push;
  авто-деплой на merge у `main`
- **Хостинг:** VPS (Ubuntu) · Nginx (reverse proxy + TLS Let's Encrypt) · Uvicorn під systemd
- **Надійність:** щоденні автоматичні бекапи БД · health-check після деплою · ротація логів
- **Спостережуваність:** структуроване логування + Sentry (трекінг помилок)

> **Підсумок:** це не прототип, а продукт, готовий до реальної експлуатації.
> → *«А тепер покажу, як це працює наживо»*
